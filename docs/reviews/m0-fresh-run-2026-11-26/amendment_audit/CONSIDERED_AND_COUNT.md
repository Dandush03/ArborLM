# M0 fresh run: amendment audit, rules considered and left counting

(Revision 2: line ranges of builders corrected after re-reading; draft 1 kept outside the deliver folder at `../work/CONSIDERED_AND_COUNT_draft1.md`.)

Every rule I considered under the amendment and left counting is below, with its reason. Under the text, a rule that is not shown counts.

All files were read at `b78e58b1f47619f070dfc6c0a88999d345b1a34b` with `git show`. Abbreviations: `S/` = `studies/m0/`; `D/` = `docs/reviews/m0-lineage-decision-2026-11-25/`. Line numbers are those of the file at that commit.

The test applied to each rule: on every item the lineage's generator can build, the rule carries out the steps a correct solver must carry out and returns the generator's answer by those steps. A rule that fails on even one item the generator can build is not the procedure. Nor is a cheaper route that happens to agree, a lookup, a fitted rule, a closed form the generator's procedure does not itself use, or a partial procedure. Where I give a counterexample item, I worked it out by hand from the builder's ranges. I ran no rule and generated no item.

## M1 (the four audit-3 rules named in section 4A stage 1S point 8, M1 bullet)

How the M1 units call these rules: they call `shortcuts_a3.spec` under the stem, except that `last_digit_power` is passed as `"power_remainder"`. See `S/m1_fix4_battery.py:118-120` and `:145` (M1a), `D/final_m1/rules_a5.py:192` (M1b) and `D/final_m1/rules_a5_attempt1.py:186` (M1c). The output name is `a3:<key>`.

### 1. `a3:k_minus_remainder_ignores_exact_fit`, lineage `M1.division_counting_r3` (stem `division_counting`): COUNTS
- Rule: `D/audit3_m1/shortcuts_a3.py:297-306`. In the `empty_seats` shape it returns `k - N % k` (line 305). In the `pallets` shape it is absent, which the M1 scripts score as a miss.
- Generator: `S/lineages_m1_fix3_b.py:351-373`. For `empty_seats`, `k = randint(8, 60+5s)` (366), `n = randint(3k, 25k+100·level)` (367) and `ans = ceil(n/k)·k − n` (368).
- Why it is not the procedure: when `n % k ≠ 0` the two agree, since `ceil(n/k)·k − n = k − n % k`. On an exact fit they differ: the answer is 0 and the rule gives `k ≥ 8`. Exact fits can be built, for example at level 0 with `k = 8` and `n = 24 = 3k`, which is in range. It also gives no answer on the pallets half of the lineage. It is a partial procedure. The `PROC` reason for its partner says "wrong only on exact fits" (`D/audit4_m1/short_summary_a4.py:11`), and so does the implementer's (`S/m1_fix3_shortcuts.py:33`, "except when N is an exact multiple of k").

### 2. `a3:largest_le_sqrt`, lineage `M1.prime_factors_r3` (stem `prime_factors`): COUNTS
- Rule: `D/audit3_m1/shortcuts_a3.py:161-169`. On the `largest` ask it builds the full trial-division factorisation `f = fac(n)` (`fac` at 31-40) and returns the largest prime factor `p` with `p² ≤ n`, falling back to `min(f)` (line 169).
- Generator: `S/lineages_m1_fix3_b.py:115-135`. It draws `n` from `_smooth(level)` (93-111): every `n` in 12..`_NMAX[level]` with all prime factors ≤ 97 and at least two distinct primes. The answer is `max(fac)` (128).
- Why it is not the procedure: it returns a different value whenever the largest prime factor exceeds √n. Example: `n = 194 = 2·97` is in `_smooth(0)` (two distinct primes, 194 ≤ 30,000). The answer is 97. The rule keeps only primes with p² ≤ 194, which gives {2}, so it returns 2. It does the factorisation and then drops a step: the cofactor above √n is never compared. The `PROC` reason says "differs from the procedure only by dropping a prime cofactor > sqrt(n)" (`short_summary_a4.py:19`), and the implementer's note says "nearly always" (`S/m1_fix3_shortcuts.py:39`). It is a partial procedure.

### 3. `a3:fermat_misapplied_e_mod_p_plus_1`, lineage `M1.last_digit_power_r3` (stem `last_digit_power`, called as `power_remainder`): COUNTS
- Rule: `D/audit3_m1/shortcuts_a3.py:174-181`. It returns `comb([pow(b, e mod (p+1), p)])`, where `comb` is the sum or the product mod p (176-177).
- Generator: `S/lineages_m1_fix3_b.py:141-162`. `p ∈ {29,37,43,47,53,59,67,79}`, `b` in 2..99+30·level with `b mod p ≠ 0` (150), `e` in 12..300+100·level (151), and `ans = Σ or Π of pow(b, e, p) mod p` (152-153).
- Why it is not the procedure: the exponent is reduced mod p+1, which is not a period of `b^e mod p`. The period divides p−1. Where `e ≤ p` the reduction is idle and the rule equals direct computation, as the `PROC` reason says (`short_summary_a4.py:22`). Where `e > p` it generally differs. Example at level 0: `p = 29`, `b = 2`, `e = 30`, all in range. The answer is `2^30 mod 29 = 2^2 = 4`, because 2^28 ≡ 1. The rule gives `pow(2, 30 mod 30, 29) = 1`. It is a misapplied reduction, not the generator's direct modular exponentiation.

### Detailed: `a4:direction_ignored_q_over_p`, `R1.equivalence_exchange_rates_r6` (units R1a and R1b, `.aud` output): COUNTS
- **Rule** (`S/r1_fix4_a4_heur.py:229-245`; `D/final_r1/a4copy/heuristics4.py:226-242`, identical body). It builds an undirected adjacency from the rates `[p, a, q, c]`, with `+1` for a→c and `−1` for c→a. It finds the BFS path from `x` to `y` (`_path`, 200-213), multiplies `N` by `q/p` on every edge **whatever the sign**, and emits the result if it is an integer (line 241).
- **Generator** (`S/lineages_r1_fix4_a.py:109-131`). Values `val` are distinct 5-smooth integers. Edges come from `_spine` (`S/lineages_r1_fix3_b.py:24-31`): spine edges `(i, i+1)` for i = 0..L−1, and extras `(existing, new)`. Each edge `(a, b)` is written as `[t·val[b]/g, items[a], t·val[a]/g, items[b]]` (124), always in the order `(a, b)`. The shuffle at 128 reorders sentences but never flips one. `x = items[0]`, `y = items[L]`, `N = (val[L]/g')·m`, and `ans = N·val[0]/val[L]` (126-127).
- **Reading.** The rate graph is a tree, so the only path from `x` to `y` is the spine 0→1→…→L. Every spine edge is traversed from its first-named item to its second, so every sign on the path is +1. Then `N·Π q_i/p_i = N·Π val[i]/val[i+1] = N·val[0]/val[L] = ans`, which is an integer by the choice of N. **So on every item the generator can build, the rule returns the generator's answer.**
- **Why it still counts.** A correct solver (the committed text-only second solver, `D/final_r1/solvers_final.py:183-210`) has to read, for each rate, which side the item it holds is on, and convert by q/p or p/q accordingly. The text promises nothing about the order in which rates are written. The rule reads the sign and throws it away. It does not carry out that step, and it returns the answer only because this generator never writes a rate against the path. It is a route that agrees through a regularity of the generator, not the lineage's procedure. Its author wrote it as a "slip" (`S/r1_fix4_a4_heur.py:236`). The correct value is computed in the same function (`v_true`) and is emitted only through the `M` rule `inverse_answer`.
- **The other reading.** The brief allows a body that differs from the procedure if it computes the same function on the generator's whole input range. Read that way, the function is the same. I apply that allowance to helpers and not to a rule that skips a step a correct solver must perform. Since there is doubt, it counts. **PENDING LEAD REVIEW** (see `REPORT.md`).

### Detailed: the closed forms of `h_venn`, `R1.venn_counting_r5` (units R1a and R1b, `.aud` with prefix `a3:` and `.impl` without): COUNT
- **Rules** (`S/r1_fix4_a3_heur.py:907-912`; `S/r1_fix3_battery.py:908-913`; `D/final_r1/a4copy/heuristics3.py:904-909`, identical). With `sz`, `pr`, `tr` the sums of the stated sizes, pairs and triples and `qd` the four-way count or 0, they compute `ignore_triples = T − sz + pr`, `sizes_minus_2pairs = sz − 2pr + 3tr − 4qd`, `pairs_minus_3triples = pr − 3tr + 6qd` and `pairs_minus_2triples = pr − 2tr + 3qd`.
- **Generator.** The ask is fixed by level: `_VENN5 = [(2,none),(2,one),(3,none),(3,two),(3,atleast_two),(4,none),(4,two)]` (350). Every region holds ≥ 1 (359). The answer is a sum of hidden regions by popcount (371).
- **Reading.** Write r_S for the regions, so that sz = Σ|S| r_S, pr = ΣC(|S|,2) r_S, tr = ΣC(|S|,3) r_S, qd = r_1234. Then:
  - `ignore_triples` equals the answer at level 0 only: T − (r1 + r2 + r12). At level 2 the answer is T − sz + pr − tr, and tr = r123 ≥ 1, so it is wrong.
  - `sizes_minus_2pairs` equals the answer at level 1 only: r1 + r2. At level 0 it gives r1 + r2 instead of the none-count.
  - `pairs_minus_3triples` equals the answer at levels 3 and 6: exactly two, with 3 and with 4 groups.
  - `pairs_minus_2triples` equals the answer at level 4 only: at least two, with 3 groups.
  - No rule in scope equals the answer at level 2 or level 5.
- **Why they count.** None is right on every item of the lineage. Each is the right closed form for one asked quantity and the wrong one for the others, so each is a partial procedure. The generator's own procedure sums regions and does not use these closed forms.
- **The consequence, by the same reading.** At levels 0, 1, 3, 4 and 6 at least one counted rule is right on every item by construction. **PENDING LEAD REVIEW** (see `REPORT.md`).
