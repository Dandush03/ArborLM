This ruling leans toward passing for the two fields it leaves unread and is reported as such.

## Added after the four stage-2 records (2026-11-26; still before any fresh item of the run or dry-run seeds exists)

- **R-52. The existing second solvers do not meet section 8 item 1, and are rewritten before the fresh run.** The four stage-2 auditors (`stage2_first_records/`) found: wording PASS for all 82 lineages; levels distinct PASS for all 82; the second solvers agree with the builders' keys on every fresh fixture item (0 mismatches in 3,500 R1, 5,950 R2, 10,150 M1 and 9,100 C1 items). But the R1, R2 and M1 text-only solvers were written from sample files that printed the builder's key under every item, for five M1 lineages the author had also read the generator's source, and the C1 "second solver" is a re-execution by an author who had audited the C1 code. Section 8 item 1 requires an author who has not read the generator's or the first solver's source and fixtures that carry no answer from the first solver. **The lead reads the builder's key as the first solver's answer** (the strict reading). The lead does not waive a written requirement; the requirement is met by rewriting: answer-free fixtures built on the generator's side, new solvers by `arbor-auditor` contexts that read neither the generators, the builders' keys nor any earlier solver, and a third context auditing each pair. For C1 the new solver evaluates the program by its own code (a tree walker over the parsed program) and does not hand the program to the interpreter's `exec`/`eval`, which is how the first solver gets its key. The stage-2 record that is hashed is rebuilt with the new solvers; the first records are kept as delivered.

## Added after the pooling script's audit (2026-11-26; still before any fresh item of the run or dry-run seeds is generated for the dry run of point 10)

- **R-56. The M1a echo rule (audit P3): a departure from the text, in the direction unfavourable to passing.** `m1_fix4_battery.py` writes one rule with its fitted positions inside its name (`echo_best_position[...]`). Under point 6 ("one rule is one name in one unit's output"), seeds that fit different positions are different names and dilute each other: the auditor's made-up case had a rule at 0.20 in every seed pooled to 2/15 and 1/15, and the lineage kept. The lead adds a second reading for every M1a key of the form `name[...]`: it is pooled as written, and also under `name` with the bracketed part removed (the rows of the three seeds summed as one rule); the larger absolute excess decides. This can only remove lineages. It is not what point 6 says and is recorded as a departure, made before any fresh figure exists, reported to the human lead with the run's report, where every lineage for which the two readings differ in outcome is listed.
- **R-57. Rates within one shape (audit P4).** Point 6 says they "are reported and not counted". The pooling script writes them into `report_extras.json` for every unit whose output carries them; they enter no decision.
- **R-58. Hash checks and stops in the tooling (audit P1, P2, P8, P10).** The runner refuses to start if any hash record of the run holds a unit that did not end with exit status 0 after its retry, records and stops on an error of its own, and checks the SHA-256 of the plan it is given against an expected value on its command line. The pooling script checks the SHA-256 of the plan, the field table and the amendment list as well as the class table and the survivor list. Dry-run exclusions are copied into the report extras.
- **R-59. R1c at the plan's item count (audit P9).** The auditor notes that the pooling of R1c can stop at the plan's item count in a way a 20-item dry run cannot show. Under the same reasoning as point 10's second paragraph, R1c is run once on the dry-run seeds at the plan's item count and its output passed through the pooling script in dry mode; only exit statuses are read, and the output files are opened by nobody. A stop there is corrected only if it is a fault of the plan or the pooling script's parsing (never of a rule or a figure), before the hashes.

The outputs of record are whatever the one run writes; reproducibility across runs is not claimed for those five scripts and is stated so in the report.
