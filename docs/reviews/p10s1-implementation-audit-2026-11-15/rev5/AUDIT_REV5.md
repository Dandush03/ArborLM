## 2. Findings

### Blocker

**B1. Item 1's runs are stopped by their item cap before they start (items 0b and 1 pooled).**
`cmd_calibrate` (`stages.py` 1005–1020) lists the 10 load-search cells first and the 12 row-U_P cells after them; the pool launches pending tasks in list order (`studies/p9/pool.py` 422–443). Every task gets `deadline = stage start + item cap`, with the item cap = 2 × the item's makespan **computed as if the item had the six workers alone, training only** (`budget.item_projection` 308–319). The training loop raises `ItemCapReached` as soon as `time ≥ deadline`, at update 1 included (`train.py` 400–401). A row-U_P run can start only after five load-search runs (262,144–524,288 updates each) have finished. a3, with the code's own caps and dispatch order, on eight sets of assumed rates (revision 4's measured rates, T-OQ ×1 or ×2, evaluation 0 or 20 s per snapshot, contention 1.0 or 1.25): **in every set all 12 row-U_P runs start at ≈ 4,876 s against an item-1 deadline of 1,828 s and are stopped at update 0**; no load-search run is stopped. Consequence: no row has a U_P → three returns to the human lead caused by scheduling, ≈ 4–5 charged hours spent, and the runs cannot be repeated (`cmd_calibrate` refuses any cell whose directory exists). Listing item 1 first removes it in all eight sets (a3, `order=row-up first`). Items 2+3 (H8 first, then dense): no run stopped in any set (H8's cap of 331 s is tight; revision 4's measured start-up plus one evaluation was 6–17 s per task). The only test of the deadline uses an already-expired deadline (`test_p10s1_rev5_model_and_guards.py` 82), and the DRY profile ignores caps, so neither the tests nor the e2e can see this.
*Fix I would accept:* per item, the cap is twice the item's projected completion time **under the exact pooled dispatch order the pool will use**, measured from the stage start (or, equivalently, the deadline counted from the item's first run start with the item's own makespan); the 12 short row-U_P tasks listed before the load-search tasks (or interleaved so that every item's projected completion is within its cap); plus a test that simulates the code's list-order dispatch with load-search runs ≫ row-U_P runs and asserts that no run's projected start or end passes its deadline, and a deadline test that is not pre-expired. Whether the cap also carries an allowance for start-up and evaluation (the preview measures neither) is **PENDING LEAD REVIEW**; revision 4's records put them at 6–103 s per task.

### Majors

**M1. The once-only calibration records can be written while the runs are still in progress.** `--finalize-items load,row-up` and `--finalize` read whatever records exist; neither requires the stage manifest (`calibrate-load-row-up/manifest.json`, `calibrate-h8-dense/manifest.json`) nor that every run of the items has a final record. a4: with both T-OQ runs at 32K/4K still running (no `train.json`), the command exits 0, writes `calibration_items_load_row_up.json` with **32K/4K: GRID_STANDS, U_L 196,608, T-OQ PREDICTED NOT LOADED**, and refuses to be applied again. For item 3 a missing record is counted as a *diverged* rate (`finalize_h8_dense`), which §25.12 item 3 does not define (it names a failed run or a chance count). This is the defect class "a once-only record written before its preconditions".
*Fix:* both finalize commands refuse unless the matching stage manifest exists and every cell of the items has a `train.json` with status `completed` or `failed` (ItemCapReached included) or is listed `not_started`/`killed_cap` in that manifest; the record lists which; a test with a missing manifest and with a run without a record.

**M2. Reading 1 (c is the larger of a rehearsal ratio and a calibration ratio) contradicts §25.12 item 2.** The ruling says the contention ratio uses the rehearsal's rates on both sides. `cmd_project` (`stages.py` 1237–1242) also takes the calibration's six-worker training rates over the isolated rates and keeps the larger c. The ADR allows the calibration to overlap another study's training (§10.3), and P10-S0 is training on this machine now; a c inflated by that overlap doubles into C_need and can trigger the cuts — cut 3 removes D-OQ at 8K/16K, a control — or NOT STARTED: BUDGET. (The rehearsal's six-worker rate also includes its first updates while the isolated rate excludes 32 warm-up updates; that biases c upward, the safe direction; informational.)
*Fix:* c from the rehearsal's six-worker training rate over the isolated rate of the same arm and slot count only; the calibration ratio recorded as descriptive; a test in which the calibration ratio is larger and does not change c.

**M3. The milestone reading is refused by a sub-label the ADR does not attach to it, and the refusal is not monotone.** `dense_at_saturation` prints both sub-labels when the ratio holds and the plateau and cost conditions both fail (the ADR prints a sub-label only when row 2 fails *only* because of one condition), and `milestone_reading` refuses "storage half supported" whenever DENSE NOT ESTABLISHED AT MATCHED COMPUTE is among the saturation sub-labels (`classes.py` 791–796). The ADR's condition is "its dense matched-compute reading is established (§22 M5)", the capacity-line dense label. a2: a store whose ratio at saturation is ≥ 1.10 with D-OQ cheaper per update is refused ("Storage-half reading not available"), while the same store with a ratio below 1.10 (no sub-label printed) is admitted ("Storage half supported"). This is a scientific reading of a positive label, not the implementer's choice. It also has to be settled **before item 0a**: the preview measures the CPU cost per update of D-OQ and of each arm at 1,024 and 4,096 slots, which is exactly what the cost condition reads (analytic D-OQ/F-OQ 1.194 at 1,024 slots, so the CPU measure decides).
*Fix (lead's choice, PENDING LEAD REVIEW):* either the ADR as written (the milestone reads only the capacity dense label's establishment; saturation sub-labels are descriptive; a sub-label only when exactly one condition fails), or a lead-ruled monotone rule (for example: the saturation cost condition failing refuses the reading whatever the ratio), recorded in the ADR before 0a, with tests of both directions.

**M4. The freeze records live P10-S0/S2 processes but does not refuse, and does not state what §25.12 item 4 requires.** The registered stages do refuse: `run_stage_tasks` calls `concurrency_guard` for every non-DRY registered stage (registered `generate` included) before the pool starts and raises `OtherStudyRunning` (exit 2); tested at `test_p10s1_rev5_model_and_guards.py` 113–114. The freeze (`stages.py` 1364) writes the list of live processes and the sentence "P10-S0's last training stage has finished if and only if the list above is empty; the lead confirms it before Decision 2". §25.12 item 4 says the freeze record *states* that S0's last training stage has finished; a conditional sentence is not that statement, and an empty process list does not establish it (between two S0 stages no `studies.p10s0` process is alive — on this machine S0's stages are driven by a shell wrapper whose command line does not contain `studies.p10s0`).
*Answer to the question asked:* yes, the freeze must refuse while an S0/S2 stage process is alive, and the statement needs evidence bound by hash: S0's manifest of its last registered training stage, or a lead's statement file. Which marker is **PENDING LEAD REVIEW** (the brief §6 item 4 asked the lead to name one; §25.12 did not).

**M5. Tests assert the repository config's pre-freeze values, so the freeze commit cannot pass its own test suite.** `test_p10s1_core.py` 175 (`cap == 16.0`), 363–366 (`r["cap_hours"] == 16.0`; `render_config_toml() == ` the repository file) and `test_p10s1_audit_fixes.py` 383–385 (generation `provisional is True`) fail as soon as `set-generation-cap` and `set-cap` rewrite the config, which the procedure does before the freeze commit; `check_preconditions` then pins `tests/test_p10s1_*` to the freeze commit. Two of these predate revision 5 (lines 143 and 412 at `3129e96`); 363–366 is new. Found by reading; not executed against a modified config.
*Fix:* assert the rule, not the value (cap = 16.0 while no projection is bound, else the computed cap of the committed projection and ≤ `cap_max_hours`; generation provisional, or measured with a manifest hash), or compare against `registered_config()` defaults rather than the repository file.
