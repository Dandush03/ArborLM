## Findings

### Blockers

None.

### Majors

**M1 — Registered mode is usable without the frozen plan, and before any freeze.** `stages.py:1055,1067`: every command other than `generate`, `check`, `rehearse` defaults to `--mode registered`. `cmd_train` (`:653`), `run_block` (`:631-643`), `cmd_gates` (`:625`), `cmd_q1_gate` (`:795`), `cmd_analyze`, `cmd_report` never call `load_plan`/`verify_plan`; only `cmd_registered` does. `check_preconditions` (`:229-254`) accepts as "freeze commit" any ancestor of HEAD whose `studies/`, config, ADR and `tests/test_p10s0_*` equal HEAD's — HEAD itself qualifies before any freeze. Demonstrated (`scripts/a7_registered_bypass.py`, preconditions and gate guards stubbed to stand for a clean post-generation state): a typed `train --block q1 --cut3 ...` in registered mode reached the pool with 190 tasks, a typed cap, no `load_plan` call and no `q1_start.json` (the headroom rule of §10.4 was never evaluated). With registered draws generated (one flag), registered seeds can be trained on by a typed command before the freeze — §14 "No registered seed is seen by a model before the freeze" and §10.2 "No registered stage is launched by a typed command" then rest on discipline only. *Fix:* registered mode reachable only through `registered <stage>`; every other command refuses `--mode registered` and none defaults to it; every worker started in registered mode re-runs `load_plan` + `verify_plan`; `check_preconditions` requires that `studies/p10s0/freeze/plan.json` exists at the freeze commit and that the freeze commit is the commit that added it. Test it in a throwaway repository.

**M2 — The registered driver accepts cap, ledger, memory and backbone overrides.** `cmd_registered` parses the common parser, so `registered q1 --stage-cap-seconds X` wins over the frozen cap (`stage_cap`, `:329-336`, returns the typed value first; run_block passes the frozen cap only as the default); `--ledger-root`/`--experiments-root` (`:84-93`) point the ledger at an empty file (16 h again); `--rss-worker-bytes`/`--rss-aggregate-bytes` raise the memory caps (`limits`, `:257-260`; "downwards only in tests" is not enforced); `--synthetic-backbone` makes `is_synthetic` true in registered mode, which trains on a random backbone and, in `work_gates` (`:433`), skips G1/G2 over the 13 draws; `--only` drops cells; `--cut3` changes the Q1 gate's analysis (`:806`); `--restore-split` changes G4. Demonstrated in `outputs/a7_registered_bypass.json` (frozen cap 100 s → 1e9 s; RSS 1 TB; synthetic backbone True; fresh ledger). The ledger's `require_room` bounded a 1e9 s cap by the remaining 16 h (failed attempt 07), which is why the demonstration uses 50,000 s. *Fix:* `cmd_registered` refuses any option whose value differs from the parser default except `--run-dir`, `--freeze-commit`, `--caps`; workers in registered mode refuse the same; the ledger root in registered mode is fixed to the default experiments root.

**M3 — A5-D's fixed strings are missing from the report's machine products.** §8.7: "wherever a class, label, annotation or hypothesis reading of A5-D is printed, the fourth-arm string of §3.4, P9-II's F1 annotation and the fixed provenance sentence are printed with it, and may not be shortened away." Producing a row-4 A5-D outcome on synthetic records (`scripts/a6_report_strings_and_nan.py`): `RESULTS.md` carries all three (the section guard works), but `classes.csv` prints `A5-D,…,RELIABLE,…,CONSISTENT ACROSS STUDIES,ADDRESS STABLE,…,True` with **none** of them (`report.py:267-275`), and `results.json` carries the fourth-arm string (via `arm_selection.fourth_arm_printed`) but **neither** the F1 annotation nor the sentence (`report.py:292`); `analysis.json` (`analysis.py:282,327`) and `q1_gate.json` (`stages.py:813-834`) carry an A5-D outcome or candidate with none. *Fix:* put the three strings as fixed fields beside every A5-D class/label/candidate in `results.json`, `analysis.json`, `q1_gate.json` and as a header block in `classes.csv`; extend `check_a5d_provenance` to every product and test it.

**M4 — A test fails once the freeze files exist, and cannot be fixed after the freeze.** `tests/test_p10s0_core.py:304-306` asserts that `plan.json` and `stage_caps.json` do not exist. The freeze commit adds both, so the suite is red at the freeze; fixing the test afterwards changes `tests/test_p10s0_*`, which `check_preconditions` (`stages.py:246-248`) compares with the freeze commit, so every registered stage would then refuse. Same defect as P9-II's (fixed there by `2bc8038`). *Fix:* assert "both or neither", as `2bc8038` does.

**M5 — Post-freeze records deadlock the run; the hour-cap delegation has no mechanism.** Any change to ADR-0020, the config, `studies/` or `tests/test_p10s0_*` after the freeze makes every registered stage refuse (`stages.py:245-250`) and turns the analysis into row 2 through `identity_mismatches` (`stages.py:569-572`; `spec_sha256` is part of `core.code_identity`, `core.py:711-715`). The ADR expects records after the freeze: §18's "separate recorded decision" before the run, and — on `claude/p10-design` (commit `f442ac7`, not yet in this branch) — the human lead's hour-cap delegation, whose limits say a raise may happen "at a stage gate that reads time and memory only" and that "each raise is recorded in the study's ADR"; S0's cap is a constant (`core.py:186`) mirrored in the hashed config. *Fix:* the README states that nothing is recorded in ADR-0020 after the freeze commit and names a post-freeze decision file outside every hashed path; if the lead wants the delegation to be usable for S0 after the freeze, the driver must read a raise from a recorded, frozen-plan-external file (old cap, new cap, projection, record path) — or the lead decides S0's cap can only be raised before the freeze. **PENDING LEAD REVIEW** (which option).

**M6 — Analysis and report can be locked out at the end of a run that obeyed the headroom rule.** Neither rule reserves the frozen caps of `analysis` and `report` (`budget.py:205-232`; `stages.py:948-949`), but both are charged and pass `ledger.require_room` (`stages.py:305`). If Q1 runs to its cap (2 × projection, which the pre-Q1 rule allows), or WX and the probe run to theirs, the remaining budget can be below the analysis cap (floor 60 s) → `analysis` and `report` are refused and no registered outcome record is written. *Fix (choice for the lead, reading A is involved):* (a) count the frozen analysis and report caps among "the stages evaluated" in both rules (most conservative); or (b) charge analysis and report without the room check. **PENDING LEAD REVIEW.**

**M7 — The registered sequence has never been executed end to end.** The DRY stage runs the non-registered commands only; `projection` → `caps` → `freeze-plan` → `registered gates` → `q1` (with `pre_q1_decision` and `q1_start.json`) → `q1_gate` (with `post_q1_decision` and the memory rule) → `wx`/`probe` → `analysis` → `report`, and `generate.sh`, have each been unit-tested in parts but never run together. P9-I and P9-II both lost an attempt to a path only the registered run exercised (`GENERATE_ATTEMPT1.md`). *Fix:* one end-to-end test in a throwaway git clone, test seed sets substituted for the registered names, executing `generate.sh` and the seven launch scripts in order from a real `freeze-plan`, with one cut, one NOT RUN — MEMORY and one refused stage.

## Rulings on the implementer's eleven PENDING LEAD REVIEW items

1. **Config filename** — *wrong.* The ADR header names `configs/p10s0_qualification.toml`; the approved ADR outranks a task message, and no recorded decision changes it. Options: rename the file and `core.DEFAULT_CONFIG` (most conservative), or the lead records an amendment before the freeze.
2. **1,800 s generation cap** — *undetermined; the lead's choice.* Only actual time is charged, but a hung draw could burn up to 1,800 s × 15 before Q1. P9-II measured about 11.6 s per draw (`P9II-ledger-A.json`). Options: keep 1,800 s as a stated engineering ceiling; or 2 × the measured generation time of the rehearsal draw (all three fact sets), floor 60 s, recorded before step 8 (most conservative).
3. **a_use over all facts** — *correct.* ADR-0021 §7.1 defines a_use as the share of usefully retained facts; this makes a_use ≤ accuracy, condition 6 (a_use ≥ 0.95 × accuracy) and i = 5 − h₂(e) − e·log₂31 consistent. Verified on a known-answer model.
4. **Rounds of six** — *correct.* §10.3 says the rehearsed projection is "arranged in rounds of six"; §10.4's perfect packing is the pre-rehearsal estimate. Rounds of six are the more conservative.
5. **Steps of §3.2 vs the §3.3 table on unrealizable combinations** — *correct.* The steps are the rule and the table is its consequence; Part 1 of the auditor's script finds no disagreement on realizable records; the script exits 1 on any disagreement.
6. **Strings the ADR does not fix** — *undetermined; the lead's choice.* On P9-II's committed records only "OVERLOAD NOT RUN — NO CANDIDATE", "NOT DEFINED (S0 NOT_EVALUATED)" and the WX "INCOMPLETE"/"NOT RUN — …" forms can occur. Most conservative: list every implementer-worded string in the freeze record and have the lead approve them before the freeze.
7. **Block order after the Q1 gate** — *undetermined; the lead's choice.* §10.2 lists "probe, WX", §13 step 9 says "WX and the probe", and the cut order treats the probe as the weaker annotation. Under the post-Q1 rule either order fits the budget. Most conservative: WX before the probe, so the higher-priority annotation completes first.
