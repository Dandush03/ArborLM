## What a run directory is

A run directory holds ONE mode, claimed in `run_mode.json` when it is first used: `registered`, `rehearsal` or `calibration`. A rehearsal or a calibration refuses the plan's registered run directory; a registered stage refuses a directory that holds another mode (`partt_stages.claim_run_dir`). No record is overwritten: a calibration run again needs `--reason` and writes `calibration_<n>.attempt<k>.json` beside the old one; every recomputation attempt is kept in `recomputation/attempt_<n>.json`, and a failed attempt stands until a lead record (`recomputation_lead_record.json`) names the cause.

## The sequence

1. **Seeds (needs the auditor): a registry revision.** Part T rehearsals train on a draw of their own and never use the registered draws. The registry must allocate, in the rehearsal range, for the Part T rehearsal training draw: ONE role (a seed for the draw of the rehearsal training material from the accepted pools, A then B, one generator), no value invented here. The code today uses the rehearsal partition seeds 252001 and 330251 + j of the config; the exact role, count and values are for the auditor to allocate (see the report of this change). Nothing registered is reused.
2. **Calibration** (MPS; about 3.7 to 7.2 h; scores D_cal only; the overlap of its draws with the registered draws is stated in its record, ruling 2): `cd "$REPO" && $Q calibrate --part-q-dir "$PQ" --run-dir "$EXP/P10IS2-T-calibration-<date>" --repetition 0`. Writes `calibration_0.json` (never overwritten; a repetition is a new record with `--reason`). Every Part T process charges `<run-dir>/charged_ledger.json`; name each such ledger later in `--charged-ledger`.
3. **Measuring rehearsal** (hours on the real data; run only when the lead says so): `sh studies/p10is2/launch/partt_rehearse.sh measuring "$EXP/P10IS2-T-measuring-<date>" --part-q-dir "$PQ" --calibration <calibration_n.json> --charged-ledger <calibration ledger>`. It drives `partt_registered.sh <stage> <run-dir> - --rehearsal --rehearsal-kind measuring --plan-file <its own plan>` for every stage in a fresh process; the stage's tasks are worker processes of the task runner, the same entry point, runner and workers as the registered run (`partt_stages.execute_stage` is the one function both call, with only `mode` differing; a test checks it). Its record `rehearsal_measuring.json` carries `caps_formula = partt-whole-process-v1`, `rates_seconds_per_unit` for every kind the plan holds, `overhead_seconds` per stage (whole-process seconds less unit work), and per worker the process-tree and own peak RSS, MPS memory, disk written, and the one-minute load at start and end, with the other studies alive. It is INCOMPLETE (and the freeze refuses it) if a kind is unmeasured.
4. **Candidate plan**: `cd "$REPO" && $Q candidate-plan --run-dir "$EXP/P10IS2-T-registered-<date>" --calibration "$EXP/P10IS2-T-calibration-<date>/calibration_0.json" --part-q-dir "$PQ" --part-q-plan "$PQPLAN" --manifests <JSON naming part_q_acceptance and panel_ledger by path and SHA-256> --charged-ledger <every Part T ledger, absolute> ...` then commit. The plan takes U, the rates, the layer and the pilot from the calibration record BY HASH, names Part Q's run directory and manifest by hash (every Part Q file Part T reads is re-hashed before use through `partt_door.PartQDoor`; a difference is PAUSED — IDENTITY), and records the charge before the freeze and the basis of the units.
5. **Caps** (by the rule; nothing typed): `cd "$REPO" && $Q caps-proposal --measuring-rehearsal <record>` prints the hours per stage and the total from the PLAN's task units (Σ units × measured rate per kind + tasks × per-process overhead; total = the charge before the freeze + 2 × all stages, rounded up to 0.01 h). Enter them in `configs/p10is2_partt.toml` `[stage_caps]` (the nine keys `gates_hours ... report_hours`, `recompute_hours`, `total_hours`) and set `caps.provisional = false` by hand (NO `caps-config` for Part T yet: NOT DONE). A cap of 0 is never "uncapped": the freeze refuses while any stage cap is 0, and a stage refuses to start without one.
6. **Counting rehearsal**: `sh studies/p10is2/launch/partt_rehearse.sh counting "$EXP/P10IS2-T-counting-<date>" --part-q-dir "$PQ"` against the candidate plan itself, through `partt_registered.sh <stage> <run-dir> - --rehearsal` in fresh processes: the plan-derived subset (replicate 0, one cell of each of the ten trained types at full U, one scoring and one combined task, the references), ONE forced pause (the cell `train|M1|AB|r0` stops after U/2 updates, exit 74, and the same command resumes it from its checkpoint) and ONE forced PAUSED — IDENTITY (the stage launched with a plan copy whose frozen hash is altered exits 75 and writes nothing; the real plan then runs). A rehearsal trains on its own draw (252002) and holds no evaluation item: `partt_rehearsal.rehearsal_bundle` splits D_cal by identity group into four disjoint parts, three standing in for E_A, E_B and E_C (the rehearsal's scores are on D_cal items only; the registry is plumbing for the analysis and the report, replicates 1 and 2 copied from 0 and listed). The cells it did not train are read from the trained cell of the same arm (`AliasMap`: order BA from AB, E-table B from A).
7. **Freeze**: `cd "$REPO" && $Q freeze --measuring-rehearsal <record> --counting-rehearsal <record> --attest-sealed-unopened lead,implementer,auditor`. It refuses provisional or zero caps; caps that differ from the rule applied to the record; a plan that differs from a re-derivation WITH the charge, the Part Q block and the calibration record the plan recorded (the differing fields are named); a calibration record that differs from its recorded hash; a ledger that holds less than the plan recorded; a Part Q manifest or plan that differs from its recorded hash.
8. **Decision 2**: `results/p10is2-partt-freeze-<date>/DECISION_2_PARTT.md` with the full freeze commit and the line `DECISION: RUN`, committed.
9. **Registered stages**, in this order, each `sh studies/p10is2/launch/partt_registered.sh <stage> <run-dir> <freeze-commit>`: `gates`, `train` (54 cells, waves, MPS; about 7 to 13 h at U = 2,000), `evaluate` (merged into `registry.json` at its end; about 5.4 h of single-worker time per pass, three workers), `controls` (checks that the registered subsamples were scored by the evaluate tasks; scores nothing again), `combined`, `recompute` (a stage with its own cap: re-scores every registered score on CPU from the stored snapshots; about 5.4 h in one process), `analysis`, `report`. Each stage refuses unless its predecessor's completion record exists (`stages/<stage>.complete.json`). The timing benchmark (`timing`) is separate and needs a quiet machine.

## What the machine must be doing

Only the timing benchmark needs a quiet machine (no study process of any study alive, one-minute load at most 2.0 for 60 s before each repetition; its own launcher, `uv` or a shell or a keep-awake watcher, counts as family and is excluded: `procs.ancestor_pids`). Every other stage shares the machine: at most 3 workers (2 while another study runs), 8 GiB per worker.

## Departures for the lead's ruling

### Ruling 6 (Q6): G1 and the Q_check groups

**What G1 requires, in the ADR's words (ADR-0025 section 8.2 and gate G1):** "Every score is on E_A or E_B: evaluation-side sentences, disjoint in identity groups from every training source ... Gate G1 requires that no evaluation reference equals a training output and that R-exact has zero hits." The ruling (Q6) adds: "Gate G1 takes the Q_check groups and keys from Part Q's partition records, read by SHA-256 from the Part Q run of record."

**What Part Q stored (file names and public keys only; no item content was opened by this work):** the bundle partition has the panels D_cal, D_con, E_A, E_B, E_C, E_open and Q_fit with their identity groups, but **no Q_check panel**. Q_check items exist only as Part Q's per-batch records `qcheck/teacher_*/block_*/batch_*.json`, whose public `keys` field lists the English keys. Those records carry no identity group per item. The ruling's "groups" are therefore not recoverable from Part Q's records.

**What my G1 checks:** (1) the P10-S2 partition gate on the bundle panels and streams, including identity-group disjointness for every item that has a group; (2) no normalized evaluation reference equals a training output and R-exact has zero hits; (3) vocabulary closure; (4) Q_check English keys, read through the checked door (each file re-hashed against Part Q's manifest), are tested for overlap with every training stream's English keys; any overlap fails G1 (ENGINEERING-FAILURE).

**What it cannot check:** identity groups of Q_check items (they carry -1, which P10-S2's gate skips). A Q_check sentence that is worded differently from every training sentence but shares an identity group with one is not detected by group.

**Could the missing groups hide a leak of a check item into training?** Yes, in one narrow way: a training item that is a paraphrase of a Q_check item (same identity group, different English key) would pass (4). It would not pass if the paraphrase were an exact key match. How likely this is I cannot state from the records. It is bounded by how Part Q drew the training pools relative to Q_check, which I did not examine. This is **PENDING LEAD REVIEW**: either accept the key-only test for Q_check, or have Part Q's group assignment for Q_check recomputed by its own code and stored (a Part Q addition, which I may not make). G1 was not weakened: the group test still runs wherever a group exists, and the added key test is stricter than before.
